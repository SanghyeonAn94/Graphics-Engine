# Discrete Event System, & Game Loop
2D, 3D같은 차원에 상관없이 게임 엔진에는 공통적으로 동작하는 Essential System이 있습니다.
## Events
엔진 입장에선 유저들은 언제 어떤 키를 누를 지 모릅니다. 여기서부터 대부분의 상호작용이 시작되는데, 키 입력 이후로 일어나는 모든 상호작용들은 전부 `Pending`됩니다. 1) 캐릭터가 주먹을 휘둘렀을 때, 2-1) 피격체가 크리쳐라면, 3-1) 피격된 대상의 프로퍼티가 적용되어 데미지를 입고 4-1) 디펜스 수치가 일정이상을 넘으면 피격 모션을 진행합니다.
혹은
2-2) 피격체가 벽이라면 3-2) 브레이커블 객체라면 이동할 수 있도록 컬리젼 옵션을 수정합니다. 4-2) 부숴지는 모션을 진행합니다.
혹은
3-3) 브레이커블 객체가 아니라면, 캐릭터를 뒤로 밀어내고 4-3) 캐릭터의 모션을 진행합니다.
---
하나의 상황임에도 무수히 많이 뻗어져 나오는 Combination을 보면 제대로 된 Event 처리를 갈망하고, 요구하게 됩니다.
## Game Loop(Polling-driven)
꼭 Event만이 아니고 매 프레임마다 동작하는 Game logic도 있을 것이고, 유저마다 달리하는 프레임에도 같은 물리법칙을 적용받기도 합니다.
우리가 배운 대부분의 역학들은 연속된 공간안에서 이루어집니다. 근데 컴퓨터는 CPU에 의해 일정 주기로서 동작하게 되는데요.
게임 엔진은 CPU보다 로직을 처리하는 주기가 길 뿐입니다.
## Event-Driven System Is Not a Subsystem of Polling-Driven System
그럼 명백히 따져봐야 합니다. 키입력을 시작으로 모든 이벤트들이 줄지어 동작된 만큼 키입력은 중요합니다. 위에서 언급한대로 게임엔진을 만드는 사람이라면 이런 입력들을 계속 모니터링할 필요가 있을텐데요. 그럼 매우 빠른 Period에서 돌고있는 키입력이라는 로직이 동작하는게 아닐까요? `피격이 일어난 경우 피격 애니메이션 출력`에서는 언제 피격이 일어나는 지, 애니메이션이 길이가 3초라면 3초가 지났는지 계속 체크해야 할 수도 있습니다. 그렇다면 Event-driven system은 주기적 호출 시스템인 Polling-driven system의 Subsystem이라고 봐야할까요?
게임 엔진은 어플리케이션입니다. 위 내용은 OS와 어플리케이션 단에서 일어나는 상황을 혼재해서 설명했습니다. 게임 엔진은 어떤 OS와 연결되어 동작할 지 모릅니다. 그러므로 우리가 현실에서 사고하는 High Level의 추상적 설계와 여러 하드웨어적 특성들을 고려한 구현들은 잘 분리되어 있어야 합니다.
게임 엔진은 규모가 큰 만큼 추상 레벨에 가까운 시스템이 있고 구현 레벨에 가까운 시스템이 있고 그 시스템마다 적용하는 패턴들이 다릅니다.
이벤트 시스템은 추상 레벨에 제일 가까운 시스템입니다.
